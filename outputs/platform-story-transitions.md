# Как сделать переходы между событиями понятнее

**Рекомендация для вебинара на 10–15 минут. Изменения из этого документа пока не внедрены.**

Главная проблема сейчас — зрителю приходится самостоятельно восстанавливать, что произошло между двумя состояниями. Например, после «CAPI заказывает машины» появляется «Подтверждаем инициализацию L1», а подпись на знакомой карточке сразу меняется. Одновременно обновляются заголовок, пояснение и результат. Простое замедление смены кадров эту смысловую паузу не объяснит.

Лучший вариант — **устойчивая схема, постоянные названия объектов и отдельное, явно показанное изменение их состояния**. Карточки сохраняют позиции внутри главы, а новые сущности дополняют уже показанные. Короткий эффект направляет внимание; текст объясняет изменение и остаётся читаемым после окончания эффекта.

На примере машин L1 стоит разделить текущую пару событий на три управляемых докладчиком шага:

| Событие | Что видит зритель | «Что изменилось» |
|---|---|---|
| **CAPI запрашивает машины** | Запрос проходит от CAPI к облаку. Видно, что заказ отправлен; существование VM ещё не утверждается. | `Описание Cluster L1 → запрос машин отправлен` |
| **Облако создаёт машины L1** | Появляются машины. Отдельная подпись сообщает: «L1 инициализируется». | `Машины запрошены → VM созданы; L1 инициализируется` |
| **Подтверждаем инициализацию L1** | Машины остаются на месте. Меняется только состояние L1. | `L1 инициализируется → L1 инициализирован` |

Один дополнительный шаг здесь оправдан: это первое знакомство аудитории с разницей между ресурсом-заявкой, виртуальными машинами и инициализированным Kubernetes. Статус «VM созданы» относится к машинам; «L1 инициализирован» — к кластеру.

Для всей презентации предлагается одна визуальная грамматика:

1. **Постоянное имя, отдельное состояние.** Названия «Машины L1», «Control plane L2», «Auth и роли» остаются неизменными. Строка состояния сообщает «запрошены», «созданы», «инициализируется», «инициализирован». Она не подменяет описание назначения объекта.
2. **Переход в существующей полосе результата.** Область «Что изменилось» показывает `предыдущее состояние → новое состояние`. Предыдущее приглушено, новое выделено. Дополнительная панель не требуется.
3. **Один эффект на одно изменение.** Новая сущность плавно появляется; у существующей карточки кратко выделяется изменившаяся строка; запрос или подтверждение один раз проходит по нужной стрелке. Остальная схема неподвижна. Ориентир для длительности — 300–700 мс.
4. **Смена внимания не означает завершение работы.** При переходе между L1 и Vault меняется акцент рассказа. Соседняя ветка не получает галочку, не останавливается и не становится готовой из-за того, что её уже показали.
5. **Ручное продвижение.** Каждый следующий смысловой шаг открывает докладчик. Автоматического перелистывания и циклических эффектов нет. Возврат и переход по навигации сразу показывают выбранное состояние без повторного «создания» всех объектов.
6. **Читаемость без движения.** При `prefers-reduced-motion` переход отображается сразу. Подписи `до → после` сохраняют весь смысл, поэтому анимация не становится обязательным условием понимания.

Где это особенно нужно:

| Часть рассказа | Как передать переход |
|---|---|
| **Заказ и зависимости** | Показать «бакет заказан → бакет создан», затем «credentials и сертификаты подготовлены → сохранены в Vault». Сохранить два независимых входа в Vault. |
| **Создание L1** | Разделить запрос, появление VM и инициализацию L1. Затем явно показать, что подтверждённая инициализация открывает bootstrap. |
| **L1 и Vault** | Фазы и настройки добавляются, обе ветки остаются частью общей подготовки. Только событие объединения подтверждает готовность обеих веток к следующему этапу. |
| **Заказ L2** | Сохранить накопительную цепочку `AddonClaim → Addon (CP) → Applications → приложение`. Новая связь и её результат появляются последовательно; одна сущность не превращается в другую. |
| **Устройство L2** | DaemonSet, общий etcd и API раскрывают устройство уже показанного приложения. Их появление в объяснении не должно выглядеть повторным созданием. Отдельное событие — возврат подтверждения инициализации в CAPI. |
| **Приложение пользователя** | Заказ пользователя запускает новую цепочку `AddonClaim → Addon → Applications → приложение`. Готовность кластера сохраняется как условие этой операции; само приложение получает отдельный результат развёртывания. |
| **Передача готового L2** | Сохранить различие: `Control plane L2 инициализирован → стандартные аддоны подготовлены → кластер готов пользователю`. |

Готовность должна обозначать конкретный подтверждённый результат. Инициализация L1 открывает bootstrap; готовность L1 вместе с настройками Vault позволяет создавать L2; инициализация Control plane L2 ещё не означает готовность пользовательского кластера. Пользовательская готовность появляется после подготовки стандартных аддонов. Положение в рассказе и пройденные пункты навигации не являются показателями состояния системы.

Между главами полезно сохранять предыдущий результат как основание следующего действия: «Зависимости подготовлены → создаём Cluster L1», «L1 и Vault подготовлены → создаём Cluster L2». Такой переход объясняет связь глав, сохраняя спокойный темп и устойчивую композицию.

# Сценарий вебинара: от заявки до готовой платформы L0–L2

Презентация: [platform-webinar.html](platform-webinar.html). Откройте HTML в современном браузере. Файл содержит всё необходимое для автономного показа; сервер и подключение к интернету для презентации не нужны.

Рассказ рассчитан на **10–15 минут, по сценарию — около 12:10**. В презентации **9 сцен, в каждой 4 последовательных раскрытия**. Начинайте с заявки: общая архитектурная карта доступна отдельной кнопкой в любой момент.

## Управление по шагам

- **→ / Page Down / пробел** — следующий шаг. После четвёртого раскрытия следующий переход открывает первую часть следующей сцены.
- **← / Page Up** — предыдущий шаг. С первого шага возврат ведёт к последнему раскрытию предыдущей сцены.
- **1–9** или пункты боковой навигации — переход к первой части выбранной сцены.
- Кнопки четырёх шагов позволяют сразу выбрать нужное раскрытие текущей сцены.
- **Home** — первая сцена, первый шаг; **End** — последняя сцена, четвёртый шаг.
- **N / Т** — показать или скрыть заметки; **F / А** — полный экран. При необходимости используйте полноэкранный режим браузера F11.
- **Esc** — закрыть открытое раскрытие или заметки.
- Нажатие на компонент открывает описание его роли. Кнопка **«Общая схема»** показывает связи L0, L1 и L2; в финале к ней ведёт и основная кнопка продолжения.

Стрелки в нижней панели также перемещают по шагам. Основная кнопка последовательно меняет действие: «Показать следующий шаг» → «Следующий этап» → «К общей схеме». Клавиша пробела на сфокусированной кнопке выполняет действие этой кнопки.

## Перед выступлением

Откройте HTML на экране, которым будете делиться, и включите полный экран. Этот сценарий удобно держать на втором экране. Встроенные заметки отображаются поверх презентации и попадут в трансляцию при показе окна; закройте их перед демонстрацией аудитории.

Раскрывайте связи по ходу объяснения. В каждой сцене первый шаг уже виден, остальные появляются по команде ведущего. Итоговый тезис появляется после четвёртого раскрытия. Длительности ниже — ориентир для речи, автоматического таймера переключения нет.

## Связи, которые важно проговорить

- **Конфигурация задаёт версию всей платформы:** сети, версии аддонов, infra и client, ресурсы мастер-нод.
- **При создании ресурса Cluster параллельно создаются служебные аддоны CSR approver и CCM.** Эта ветка есть и у infra, и у client. Оба компонента находятся в **L0**: CSR approver отвечает за подпись сертификатов нод, CCM — за интеграцию с облаком.
- **После infra initialized запускается bootstrap L1.** Дальше AddonOperator управляет фазами Argo CD Applications: mTLS, сетевые политики, мониторинг и логи; host firewall с default deny завершает настройку.
- **Hardening L1 и подготовка Vault выполняются параллельно.** В Vault готовятся ServiceAccount auth, точечные роли, индивидуальные высокоэнтропийные секреты и KMS transit для L2.
- **Готовность аддонов L1 открывает создание client.** Его control plane разворачивается как DaemonSet на нодах infra, использует общий etcd L1 и отдельный префикс для данных L2.
- **Подтверждение инициализации в CAPI — отдельный этап.** Пользователь получает готовый кластер после развёртывания стандартных аддонов L2: Cilium, CoreDNS и Konnectivity.

## 1. Одна заявка. Вся конфигурация. — 01:10

**На экране:** ClusterClaim задаёт версию платформы: сети, версии аддонов, infra и client, а также ресурсы мастер-нод. Вместе эти параметры определяют целевую конфигурацию.

**Четыре раскрытия:**

1. Заказ → ClusterClaim
2. Параметры сети
3. Версии addons / infra / client
4. Ресурсы master nodes

Начните с того, что именно мы создаём. Вся целевая конфигурация задаёт версию платформы: сетевые параметры, версии инфраструктурного и клиентского Kubernetes, версии аддонов и ресурсы мастер-нод. Заявка ClusterClaim находится в управляющем кластере L0.

Последовательно раскройте три группы параметров. Это помогает отделить намерение от исполнения: сначала мы задаём, какой результат нужен, затем операторы разворачивают описание в ресурсы и доводят их до нужного состояния.

Дальше рассказ пойдёт по пути одной такой заявки. L0 координирует процесс, L1 станет инфраструктурной основой, а L2 — клиентским Kubernetes. Общую карту уровней можно открыть отдельно в любой момент.

**Тезис сцены:** Целевая конфигурация задаёт версию всей платформы.

## 2. Подготавливаем доверие и доступы. — 01:10

**На экране:** Платформа подготавливает сертификаты, создаёт S3-бакет для резервных копий и сохраняет данные доступа в Vault. Эти зависимости потребуются следующим компонентам.

**Четыре раскрытия:**

1. ClusterClaimOperator
2. Сертификаты
3. S3 backup bucket
4. Credentials → Vault

Первый этап после заявки — подготовка внешних зависимостей. Платформа выпускает необходимые сертификаты и создаёт бакет для резервных копий. Покажите эти действия отдельно: сертификаты дают основу для доверенных соединений, бакет становится доступным ресурсом платформы.

Затем раскройте передачу credentials в Vault. Данные доступа должны оказаться в хранилище секретов, откуда их получат соответствующие компоненты. Так сведения о доступах связываются с конкретной создаваемой платформой.

На этой сцене важно показать порядок подготовки. Пока мы ещё не передаём клиенту Kubernetes: мы создаём необходимые условия для дальнейшего развёртывания инфраструктуры и её сервисов. Следующая сцена переводит заявку в инфраструктурный кластер.

**Тезис сцены:** Сертификаты, хранилище и данные доступа готовятся до запуска следующих компонентов.

## 3. L1 получает свою основу. — 01:25

**На экране:** В L0 вместе с Cluster infra создаются аддоны CSR approver и CCM. CAPI создаёт машины L1. После infra initialized запускается bootstrap: Cilium, CoreDNS, Argo CD и AddonOperator.

**Четыре раскрытия:**

1. Cluster infra и служебные аддоны
2. CAPI
3. Машины L1 · инициализация
4. Bootstrap-компоненты

Заявка превращается в Cluster infra. В L0 параллельно с ресурсом Cluster создаются служебные аддоны: CSR approver для подписи сертификатов нод и CCM для интеграции с облаком. Покажите две ветки одновременно.

По основной ветке Cluster API подхватывает описание, создаются виртуальные машины и разворачивается инфраструктурный Kubernetes. Сначала подтверждается infra initialized. Затем запускается bootstrap: Cilium, CoreDNS, Argo CD и AddonOperator.

Bootstrap даёт сеть, DNS и средства дальнейшего развёртывания. Служебная ветка CSR approver и CCM начинается вместе с Cluster и имеет собственную задачу. После исходного набора L1 последовательно получает остальные аддоны, политики и настройки платформы.

**Акцент на параллельной ветке:** CSR approver и CCM находятся в L0. Они создаются вместе с ресурсом Cluster и сопровождают соответствующий infra- или client-кластер. Раскрывайте эту связь одновременно с появлением Cluster.

**Тезис сцены:** Bootstrap создаёт основу, на которой платформа сможет развернуть остальные аддоны.

## 4. Аддоны запускаются в нужном порядке. — 01:40

**На экране:** AddonOperator управляет фазами Argo CD Applications: mTLS, сетевые политики, мониторинг и логи. Завершает настройку host firewall с default deny.

**Четыре раскрытия:**

1. Addon → AddonOperator → Applications
2. mTLS и сетевые политики
3. Monitoring + logging
4. Host firewall + default deny

Теперь приблизьте AddonOperator. Он работает над Applications в Argo CD и задаёт фазы, зависимости и очередность. Благодаря этому состав платформы появляется последовательно, с учётом того, что должно быть подготовлено к запуску следующего компонента.

В этом процессе настраиваются mTLS и сетевые политики, разворачиваются мониторинг и сбор логов. Раскройте группы по очереди: зрителю важно увидеть управляемый порядок и назначение каждой группы, а не запомнить все имена ресурсов.

Завершающее действие — host firewall с политикой default deny. Подчеркните его положение в конце этой последовательности. На следующей сцене покажем ещё одну ветку работы, которая выполняется параллельно этому доведению и усилению защиты L1.

**Тезис сцены:** Порядок развёртывания позволяет завершить L1 строгими сетевыми ограничениями.

## 5. Vault готовит доступы и ключи. — 01:25

**На экране:** Параллельно настройке L1 в Vault создаются SA auth, точечные роли, индивидуальные высокоэнтропийные секреты и KMS transit для L2.

**Четыре раскрытия:**

1. Параллельно L1 + VaultAuth
2. SA и точечные роли
3. Уникальные секреты
4. KMS Transit Key

Эта ветка идёт параллельно работе AddonOperator над L1. Переведите внимание на Vault: здесь настраивается аутентификация через ServiceAccount и создаются точечные роли, соответствующие задачам отдельных компонентов. На схеме сохраните видимой параллельную ветку аддонов.

Далее создаются индивидуальные секреты с высокой энтропией. Объясните смысл без демонстрации значений: каждый компонент получает собственные данные доступа и необходимый ему набор прав. Так конфигурация доступов привязана к ролям внутри платформы.

Для будущего L2 также подготавливается KMS transit. К моменту запуска клиентского control plane у него должны быть готовы необходимые ключи и доступы. После подготовки зависимостей обе ветки сходятся перед переходом к созданию client.

**Тезис сцены:** У компонентов свои права и секреты; ключи для L2 подготовлены к его запуску.

## 6. L1 готов. Запускаем client. — 01:25

**На экране:** После готовности аддонов L1 в L0 создаются Cluster client и параллельные аддоны CSR approver и CCM. Через CAPI и AddonClaim разворачивается client-control-plane в infra.

**Четыре раскрытия:**

1. L1 addons готовы
2. Cluster client и служебные аддоны
3. AddonClaim
4. Addon client-control-plane L1

Начните с барьера: аддоны L1 готовы. Только после этого создаётся Cluster client. Вместе с ним в L0 запускаются параллельные служебные аддоны: CSR approver для подписи сертификатов нод и CCM для интеграции с облаком.

Проследите основную цепочку: Cluster client, Cluster API, AddonClaim. Заявка на аддон приводит к появлению client-control-plane в infra-кластере. Служебную ветку сохраните видимой сбоку, чтобы показать одновременность действий при создании Cluster.

Клиентский Kubernetes описан через Cluster API, а управляющие компоненты доставляются как приложение в L1. Стандартные Cilium, CoreDNS и Konnectivity появятся позже в L2. Сейчас переходим к размещению control plane и хранению его состояния.

**Акцент на параллельной ветке:** CSR approver и CCM находятся в L0. Они создаются вместе с ресурсом Cluster и сопровождают соответствующий infra- или client-кластер. Раскрывайте эту связь одновременно с появлением Cluster.

**Тезис сцены:** Готовность аддонов L1 открывает переход к клиентскому control plane.

## 7. Control plane L2 — приложение в L1. — 01:40

**На экране:** Клиентский control plane работает как DaemonSet на нодах infra. Он использует общий etcd L1 и хранит данные в отдельном префиксе.

**Четыре раскрытия:**

1. Infra nodes L1
2. DaemonSet clientCP
3. Общий etcd L1
4. Отдельный префикс L2 / API

Приблизьте границу L1. Клиентский control plane развёрнут как обычное приложение: DaemonSet размещает его на нодах infra-кластера. При этом компоненты предоставляют API отдельного клиентского Kubernetes — L2. Место исполнения и обслуживаемый кластер показаны разными связями.

Теперь раскройте связь с etcd. Для состояния используется общий etcd инфраструктурного кластера. Данные клиентского control plane размещаются в отдельном префиксе: это разделение пространства ключей внутри используемого хранилища.

Удержите на экране одновременно приложение, etcd и клиентский API. Эта сцена объясняет центральную архитектурную идею: жизненным циклом управляющих компонентов L2 можно управлять средствами L1, а клиент взаимодействует с собственным Kubernetes API.

**Тезис сцены:** Отдельный клиентский API опирается на управляющие компоненты и etcd внутри L1.

## 8. Control plane создан. CAPI получает статус. — 01:00

**На экране:** Состояние control plane возвращается в Cluster API, и Cluster отмечается созданным. Далее платформа доводит клиентский кластер до передачи пользователю.

**Четыре раскрытия:**

1. clientCP initialized
2. Статус CAPI
3. Cluster client initialized
4. Переход к аддонам L2

После запуска control plane его состояние проходит обратно по цепочке управления. Cluster API получает подтверждение, и объект Cluster отражает результат создания. Анимация теперь движется от работающего компонента к описывающему его ресурсу.

Подчеркните конкретный результат этого этапа: клиентский control plane создан и его инициализация подтверждена. Платформа получила основание перейти к развёртыванию стандартных компонентов в клиентском Kubernetes. Для истории это переход от создания управления к подготовке среды пользователя.

Не задерживайтесь на служебных именах условий. Лучше показать понятную отметку «Cluster создан» и следующий шаг. Пользователь получит готовый кластер после того, как в L2 появится предусмотренный набор базовых аддонов.

**Тезис сцены:** Создание control plane подтверждено; следующим шагом готовится стандартный состав L2.

## 9. Базовые аддоны. Готовый L2. — 01:15

**На экране:** В L2 через AddonClaim разворачивается стандартный набор: Cilium, CoreDNS и Konnectivity. После его подготовки пользователь получает готовый кластер.

**Четыре раскрытия:**

1. AddonClaim для L2
2. Cilium / CoreDNS
3. Konnectivity
4. Выдача пользователю

Последняя сцена переносит внимание с управляющих компонентов на сам клиентский кластер. Через AddonClaim в L2 разворачивается стандартный состав: Cilium, CoreDNS и Konnectivity. Покажите эти компоненты внутри логической границы L2.

Здесь важно завершить начатую историю: заявка описывала платформу целиком, поэтому процесс включает и подготовку клиентской среды. После стандартных аддонов пользователь получает готовый Kubernetes и может переходить к своим приложениям.

В конце откройте общую карту, если нужно повторить роли уровней: L0 координирует создание, L1 размещает инфраструктуру и client control plane, L2 предоставляет клиентский Kubernetes. На карте теперь можно проследить весь путь одной заявки и вернуться к любому компоненту для вопросов.

**Тезис сцены:** Путь заканчивается готовым клиентским Kubernetes со стандартными компонентами платформы.

## Архитектурная основа

Полная последовательность и устройство платформы основаны на уточнённом описании её команды. L0 — управляющий кластер; L1 — инфраструктурный кластер; L2 — клиентский Kubernetes, чей control plane работает в L1. CSR approver и CCM исполняются в L0. Сцены отражают описанный командой сценарий вместе с Vault и KMS.

[Репозиторий cluster-claim-operator](https://github.com/PRO-Robotech/cluster-claim-operator) показывает часть оркестрации. Для полной схемы использовано описание команды, включая bootstrap, порядок аддонов, параллельные ветки, размещение DaemonSet, общий etcd и финальную подготовку L2.

Презентация иллюстрирует архитектуру и процесс создания. Она не подключена к живому кластеру: раскрытия и статусы управляются ведущим, а переключение шагов не обращается к инфраструктуре.

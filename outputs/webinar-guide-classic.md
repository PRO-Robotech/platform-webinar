# Путь кластера · Classic — сценарий вебинара

[Открыть презентацию](platform-webinar-classic.html)

Все сохранённые оформления используют единый актуальный флоу: **7 глав, 36 событий**, около **14:30**. Сценарий и схемы формируются из общих исходников; обозначение v1 сохраняет название оформления.

**Уровни:** L0 — управляющий кластер; L1 — инфраструктурный; L2 — клиентский. Пользователь — отдельный участник процесса.

## Управление

- **← / →** — предыдущее / следующее событие.
- **1–7** или нижняя навигация — выбор главы.
- **Home / End** — начало / конец рассказа.
- Нажатие на блок — его описание.
- **F** — полноэкранный режим.

Переходы выполняет ведущий. Параллельные процессы рассматриваются по очереди только для удобства объяснения.

## Опорные связи

- ClusterClaim Operator наблюдает ClusterClaim; стрелка направлена от оператора к ресурсу. Оператор создаёт Cluster и CSR approver / CCM в L0 для L1 и L2.
- Cluster API наблюдает ресурс Cluster и запускает создание машин или control plane. Статус инициализации L1 возвращается через Cluster L1 в ClusterClaim.
- Аддоны проходят фазы установки, защиты, наблюдаемости и изоляции. Одновременно ClusterClaim Operator настраивает Vault для конкретного кластера.
- Control plane L2 разворачивается по цепочке AddonClaim → Addon (CP) → Applications → приложение в L1.
- Статус возвращается по цепочке Control plane L2 → Applications → Addon (CP) → AddonClaim → Cluster L2 → ClusterClaim.
- Базовые аддоны L2 заказывает ClusterClaim Operator. Пользовательские приложения проходят ту же цепочку AddonClaim → Addon → Applications → итоговые ресурсы.
- Vault хранит подготовленные зависимости и индивидуальные настройки доступа для кластера.

## 1. От заказа к зависимостям — 02:15

Что должно появиться до создания инфраструктуры?

### 01. Собираем версию платформы

[Показать шаг](platform-webinar-classic.html#chapter-1-step-1)

Сети, версии аддонов, L1 и L2, ресурсы мастеров собираются в ClusterClaim. Эта конфигурация задаёт версию платформы.

**Результат:** Целевая конфигурация записана в ClusterClaim в L0.

Начните с заказа L2. Покажите, что версия платформы включает весь состав: сетевые параметры, версии Kubernetes и аддонов, ресурсы мастер-нод. Эти параметры становятся одной заявкой ClusterClaim в L0. С этого момента будем следить за результатами работы над одной заявкой.

### 02. Передаём заявку оператору

[Показать шаг](platform-webinar-classic.html#chapter-1-step-2)

ClusterClaim Operator читает конфигурацию и начинает подготовку. Заявка превращается в действия над зависимостями.

**Результат:** Оператор начал подготовку ресурсов по заявке.

Оставьте заявку на месте и покажите её связь с оператором. Именно оператор переводит желаемую конфигурацию в ресурсы и дальнейшие действия. Сейчас его задача — подготовить зависимости, которые понадобятся создаваемой платформе. Следующие моменты раскроют каждую из них.

### 03. Заказываем бакет у облака

[Показать шаг](platform-webinar-classic.html#chapter-1-step-3)

Оператор запрашивает S3-бакет для резервных копий. Облако создаёт бакет и возвращает необходимые данные доступа.

**Результат:** Созданы backup-бакет и credentials для доступа к нему.

Проследите оба направления связи: запрос от платформы в облако и ответ с результатом. В результате появляется бакет для резервных копий и данные доступа к нему. Сам бакет остаётся ресурсом облака; его credentials следующим шагом попадут в Vault.

### 04. Подготавливаем сертификаты

[Показать шаг](platform-webinar-classic.html#chapter-1-step-4)

Система сертификатов подготавливает материал доверия для компонентов. Сертификаты становятся ещё одной зависимостью платформы.

**Результат:** Сертификаты для компонентов подготовлены.

Переведите внимание на вторую зависимость — сертификаты для компонентов платформы. Их подготовка создаёт основу доверенных соединений. Порядок объяснения бакета и сертификатов не задаёт зависимость выпуска сертификатов от бакета: на схеме между ними не требуется последовательная стрелка.

### 05. Сохраняем зависимости в Vault

[Показать шаг](platform-webinar-classic.html#chapter-1-step-5)

Credentials бакета и подготовленные сертификаты записываются в Vault. Они будут доступны следующим компонентам платформы.

**Результат:** Vault хранит данные доступа к бакету и сертификаты.

Покажите состав зависимостей в Vault: данные доступа к бакету и подготовленные сертификаты. Содержимое секретов показывать не нужно — достаточно назначения. Сделайте короткую паузу: у заявки появились необходимые зависимости, теперь можно переходить к инфраструктуре.

## 2. Из ресурса появляется L1 — 02:15

Как описание кластера превращается в работающую основу?

### 06. Создаём Cluster L1

[Показать шаг](platform-webinar-classic.html#chapter-2-step-1)

ClusterClaim Operator читает ClusterClaim и создаёт Cluster L1. Параллельно он создаёт CSR approver и CCM в L0.

**Результат:** По ClusterClaim созданы Cluster L1, CSR approver и CCM в L0.

Начните с ClusterClaim: заявка задаёт желаемое состояние всего процесса. ClusterClaim Operator создаёт по ней Cluster L1, который подхватит CAPI. Параллельно в L0 создаются CSR approver для подписи сертификатов нод и CCM для интеграции с облаком. Сохраните исходную заявку видимой: сюда вернётся статус L1.

### 07. CAPI заказывает машины

[Показать шаг](platform-webinar-classic.html#chapter-2-step-2)

Cluster API подхватывает созданный Cluster L1 и заказывает у облака виртуальные машины для L1.

**Результат:** Облако создало виртуальные машины L1.

Сначала покажите ClusterClaim Operator: он читает ClusterClaim и создаёт Cluster L1 и служебные CSR approver/CCM в L0. Затем проведите взгляд от Cluster L1 через CAPI к облаку. После запроса появляются виртуальные машины, из которых формируется L1. Служебная ветка CSR approver и CCM остаётся в L0; переход внимания к машинам не переносит эти компоненты в L1.

### 08. Подтверждаем инициализацию L1

[Показать шаг](platform-webinar-classic.html#chapter-2-step-3)

Статус L1 проходит через CAPI и Cluster L1 в ClusterClaim. В заявке отражено «L1 инициализирован»; далее начинается bootstrap.

**Результат:** ClusterClaim отражает инициализацию L1.

Проследите обратную цепочку: L1 → CAPI → Cluster L1 → ClusterClaim. Фактическая инициализация отражается в исходной заявке, которая задала желаемое состояние. После подтверждения «L1 инициализирован» начинается bootstrap. Сделайте короткую паузу между появлением машин и подтверждённым результатом.

### 09. Запускаем сеть и DNS

[Показать шаг](platform-webinar-classic.html#chapter-2-step-4)

После инициализации L1 bootstrap устанавливает Cilium и CoreDNS. L1 получает сеть и DNS.

**Результат:** В составе bootstrap L1 появились Cilium и CoreDNS.

Раскройте первую часть исходного набора: Cilium и CoreDNS. Объясните их назначение коротко — сеть и DNS для L1. Следующим моментом раскроются средства доставки. Это разделение помогает объяснить состав bootstrap и не вводит дополнительный барьер между его компонентами.

### 10. Включаем доставку аддонов

[Показать шаг](platform-webinar-classic.html#chapter-2-step-5)

Bootstrap также устанавливает Argo CD и AddonOperator. В L1 появляются средства доставки компонентов и управления их очередностью.

**Результат:** Argo CD и AddonOperator вошли в исходный состав L1.

Теперь добавьте Argo CD и AddonOperator к уже знакомым компонентам bootstrap. У L1 есть средства, с помощью которых можно разворачивать последующий состав платформы. Следующая глава показывает, как AddonOperator ведёт фазы Applications и как параллельно готовятся доступы в Vault.

## 3. Две ветки готовят платформу — 03:10

Что готовится одновременно перед запуском L2?

### 11. Устанавливаем аддоны L1

[Показать шаг](platform-webinar-classic.html#chapter-3-step-1)

AddonOperator ведёт фазы L1 через Argo CD Applications. Параллельно ClusterClaimOperator из L0 настраивает внешний Vault.

**Результат:** Идут фазы L1; ClusterClaimOperator параллельно настраивает Vault для этого кластера.

Покажите две ветки и их исполнителей. В L1 AddonOperator управляет фазами через Argo CD Applications. Из L0 ClusterClaimOperator отправляет запросы во внешний Vault и настраивает его индивидуально для этого кластера. Vault хранит данные и предоставляет механизмы auth и transit. Порядок рассказа не означает ожидание одной ветки другой.

### 12. Настраиваем mTLS и политики

[Показать шаг](platform-webinar-classic.html#chapter-3-step-2)

Фазы аддонов настраивают mTLS и сетевые политики в L1. Компоненты получают предусмотренную защиту соединений и сети.

**Результат:** В L1 применяются mTLS и сетевые политики.

Выделите ветку L1, сохраняя видимой связь ClusterClaimOperator из L0 с внешним Vault. Объясните назначение фазы: настроить защищённые соединения и сетевые политики компонентов. Затем переводите внимание к запросам оператора в Vault. Оба процесса выполняются параллельно.

### 13. Настраиваем вход и роли в Vault

[Показать шаг](platform-webinar-classic.html#chapter-3-step-3)

ClusterClaimOperator из L0 регистрирует кластер в Vault auth, создаёт точечные роли и привязывает ServiceAccount L1.

**Результат:** ClusterClaimOperator настроил в Vault auth, роли и привязки ServiceAccount L1.

Теперь рассматриваем действие ClusterClaimOperator в L0. Оператор регистрирует этот кластер в Vault auth, создаёт точечные роли и привязки ServiceAccount L1. Внешний Vault предоставляет механизм аутентификации и сохраняет настройки. Так идентичность компонента связывается с нужными правами; фазы L1 продолжаются параллельно.

### 14. Добавляем мониторинг и логи

[Показать шаг](platform-webinar-classic.html#chapter-3-step-4)

Следующая показанная фаза L1 разворачивает мониторинг и сбор логов. Платформа получает средства наблюдения за компонентами.

**Результат:** В L1 развёрнуты мониторинг и сбор логов.

Верните внимание к L1. В составе платформы появляются мониторинг и сбор логов. Здесь достаточно назначения и названий групп компонентов: реальные показатели не нужны. Две ветки по-прежнему видны, поэтому возврат к инфраструктуре воспринимается как смена фокуса внутри одной подготовки.

### 15. Создаём индивидуальные секреты

[Показать шаг](platform-webinar-classic.html#chapter-3-step-5)

ClusterClaimOperator создаёт в Vault индивидуальные высокоэнтропийные секреты для кластера. Vault хранит эти данные.

**Результат:** ClusterClaimOperator создал индивидуальные секреты этого кластера в Vault.

ClusterClaimOperator создаёт индивидуальные высокоэнтропийные секреты для этого кластера и сохраняет их во внешнем Vault. Покажите направление запроса из L0 к хранилищу. Подчеркните связь между компонентом, его ролью и предназначенным ему секретом; значения секретов не требуются.

### 16. Готовим KMS для L2

[Показать шаг](platform-webinar-classic.html#chapter-3-step-6)

ClusterClaimOperator из L0 настраивает в Vault KMS transit для L2. Ключ и доступы готовятся до запуска control plane L2.

**Результат:** ClusterClaimOperator подготовил KMS transit для L2 во внешнем Vault.

Покажите ещё один запрос ClusterClaimOperator из L0: оператор настраивает KMS transit для L2 во внешнем Vault. Vault предоставляет механизм transit и хранит подготовленные ключи. Настройки создаются индивидуально для этого кластера до запуска control plane L2. Фазы аддонов L1 идут параллельно.

### 17. Включаем host firewall

[Показать шаг](platform-webinar-classic.html#chapter-3-step-7)

Завершающая фаза L1 включает host firewall с default deny. Финальные сетевые ограничения применяются после подготовки компонентов.

**Результат:** Host firewall с default deny завершает настройку L1.

Явно обозначьте положение host firewall в конце фаз L1. Политика default deny — завершающее действие этой ветки после подготовки состава и настроек. На схеме это последний узел очереди L1; Vault остаётся соседней веткой со своими готовыми результатами.

### 18. Собираем условия для L2

[Показать шаг](platform-webinar-classic.html#chapter-3-step-8)

Аддоны L1 готовы. ClusterClaimOperator подготовил в Vault настройки этого кластера: доступы, секреты и KMS transit для L2.

**Результат:** Можно переходить к созданию Cluster L2.

Сведите в L0 результаты двух веток: готовые аддоны L1 и настройки, созданные ClusterClaimOperator во внешнем Vault для этого кластера. Сделайте паузу на условиях перехода. Следующий этап — создание Cluster L2 в L0. Vault остаётся внешним хранилищем и поставщиком механизмов, а инициатор настройки — оператор.

## 4. Заказываем control plane L2 — 01:50

Как заказ кластера становится приложением в L1?

### 19. Создаём Cluster L2

[Показать шаг](platform-webinar-classic.html#chapter-4-step-1)

После готовности L1 ClusterClaim Operator читает ClusterClaim и создаёт в L0 Cluster L2, CSR approver и CCM.

**Результат:** ClusterClaim Operator создал Cluster L2 и его служебные компоненты в L0.

Вернитесь к исходному ClusterClaim в L0. ClusterClaim Operator читает заявку и после готовности L1 создаёт две параллельные ветки: Cluster L2 и служебные CSR approver/CCM для L2. Оба контроллера работают в L0. Далее Cluster L2 подхватит Cluster API.

### 20. CAPI создаёт AddonClaim

[Показать шаг](platform-webinar-classic.html#chapter-4-step-2)

Cluster API подхватывает Cluster L2 и приводит к созданию AddonClaim. Control plane L2 заказан как аддон платформы.

**Результат:** Появилась заявка AddonClaim на control plane L2.

Проследите цепочку от Cluster L2 через CAPI к AddonClaim. Здесь соединяются две модели: L2 описывается кластерным ресурсом, а его управляющие компоненты заказываются как аддон. Следующим результатом обработки AddonClaim станет ресурс Addon (CP) в L1.

### 21. Создаём Addon (CP) в L1

[Показать шаг](platform-webinar-classic.html#chapter-4-step-3)

Контроллер AddonClaim создаёт ресурс Addon (CP) в L1. Этот ресурс описывает аддон, из которого будет развёрнут Control plane L2.

**Результат:** В L1 создан ресурс Addon (CP).

Сохраните AddonClaim видимым и покажите результат его обработки — ресурс Addon (CP) внутри L1. Пока это описание аддона. Следующим исполнителем становится AddonOperator, который подхватит этот ресурс и подготовит Applications.

### 22. Создаём Applications

[Показать шаг](platform-webinar-classic.html#chapter-4-step-4)

AddonOperator подхватывает Addon (CP) в L1 и создаёт Applications. Они описывают компоненты, которые затем развернёт Argo CD.

**Результат:** AddonOperator создал Applications для Control plane L2.

Проведите связь от Addon (CP) к AddonOperator и затем к появляющимся Applications. Здесь важно назвать исполнителя: Applications создаёт AddonOperator на основе ресурса Addon. Дальнейшее развёртывание выполняет Argo CD.

### 23. Разворачиваем Control plane L2 в L1

[Показать шаг](platform-webinar-classic.html#chapter-4-step-5)

Argo CD обрабатывает созданные Applications и разворачивает приложение Control plane L2 в L1. Цепочка доставки завершена.

**Результат:** Argo CD развернул приложение Control plane L2 в L1.

Покажите последнее действие: Argo CD получает Applications и разворачивает приложение Control plane L2 в L1. Сохраните видимой цепочку AddonClaim → Addon (CP) → AddonOperator → Applications → Argo CD. Затем переходите к устройству приложения: DaemonSet и связи с etcd.

## 5. Показываем устройство L2 — 02:00

Где работают компоненты L2 и хранится его состояние?

### 24. Размещаем control plane L2 на нодах L1

[Показать шаг](platform-webinar-classic.html#chapter-5-step-1)

DaemonSet размещает control plane L2 на нодах L1. Управляющие компоненты L2 работают как обычное приложение внутри L1.

**Результат:** Control plane L2 работает на нодах L1 как DaemonSet.

Раскройте внутреннее устройство приложения: control plane L2 размещён на нодах L1 как DaemonSet. Подпись «работает в L1» должна оставаться рядом с компонентом. Показанное число условных нод не задаёт число реплик; смысл кадра — механизм и место исполнения.

### 25. Выделяем префикс в общем etcd

[Показать шаг](platform-webinar-classic.html#chapter-5-step-2)

Control plane L2 использует общий etcd L1. Данные L2 размещаются в отдельном префиксе.

**Результат:** Состояние L2 хранится в etcd L1 под отдельным префиксом.

Покажите связь приложения с уже существующим etcd L1. Для данных L2 используется отдельный префикс внутри общего хранилища. Остановитесь на этой схеме на несколько секунд. Отдельный префикс объясняет разделение пространства ключей; дополнительных свойств изоляции из него выводить не нужно.

### 26. Открываем API L2

[Показать шаг](platform-webinar-classic.html#chapter-5-step-3)

Компоненты control plane исполняются в L1. API L2 — точка доступа к ним для управления клиентским кластером.

**Результат:** API L2 — интерфейс доступа; запросы обслуживает control plane в L1.

Покажите логическую плоскость L2 и проведите к ней связь от control plane L2. Само приложение остаётся внутри L1. Так аудитория видит одновременно место исполнения компонентов и отдельный кластер, которым они управляют. Это центральное различие всей архитектуры.

### 27. Возвращаем статус в ClusterClaim

[Показать шаг](platform-webinar-classic.html#chapter-5-step-4)

Статус Control plane L2 проходит через Applications → Addon (CP) → AddonClaim → Cluster L2 и возвращается в ClusterClaim.

**Результат:** Инициализация L2 отражена в ClusterClaim.

Проследите всю обратную цепочку: Control plane L2 → Applications → Addon (CP) → AddonClaim → Cluster L2 → ClusterClaim. Applications и Addon находятся в L1, AddonClaim и последующие ресурсы управления — в L0. Каждый следующий участник получает статус предыдущего. Исходная заявка отражает подтверждённую инициализацию L2. Это состояние управляющих компонентов; финальная готовность и передача L2 пользователю следуют после развёртывания стандартных аддонов.

## 6. Доводим L2 и передаём пользователю — 01:50

Что превращает созданный control plane L2 в готовый кластер?

### 28. Заказываем базовые аддоны L2

[Показать шаг](platform-webinar-classic.html#chapter-6-step-1)

ClusterClaim Operator в L0 создаёт AddonClaim на базовые аддоны L2. Заявка запускает доставку через компоненты L1.

**Результат:** ClusterClaim Operator создал AddonClaim для базовых аддонов L2 в L0.

Покажите инициатора: ClusterClaim Operator в L0 создаёт AddonClaim на базовые аддоны L2. Оператор запускает подготовку стандартного набора. Дальше проследите цепочку через L1 к результату в L2: AddonClaim, Addon, Applications и развёрнутые компоненты.

### 29. Создаём Addon для L2 в L1

[Показать шаг](platform-webinar-classic.html#chapter-6-step-2)

Контроллер AddonClaim создаёт Addon в L1. Ресурс описывает стандартные аддоны, которые предстоит развернуть в L2.

**Результат:** В L1 создан Addon для базовых компонентов L2.

Сохраните AddonClaim в L0 и покажите результат его обработки — ресурс Addon внутри L1. Он описывает будущие компоненты L2. Это вход для AddonOperator; сами Cilium, CoreDNS и Konnectivity появятся после обработки Applications.

### 30. Создаём Applications для L2

[Показать шаг](platform-webinar-classic.html#chapter-6-step-3)

AddonOperator в L1 подхватывает Addon и создаёт Applications. Они задают Argo CD развёртывание базовых компонентов в L2.

**Результат:** В L1 созданы Applications для доставки компонентов в L2.

Покажите исполнителя: AddonOperator читает ресурс Addon и создаёт Applications в L1. Цель этих Applications — ресурсы в L2. Сохраните всю цепочку видимой: AddonClaim в L0, затем Addon и Applications в L1.

### 31. Готовим стандартный набор L2

[Показать шаг](platform-webinar-classic.html#chapter-6-step-4)

Argo CD в L1 обрабатывает Applications и разворачивает ресурсы Cilium, CoreDNS и Konnectivity в L2. Базовый набор готов.

**Результат:** Argo CD развернул Cilium, CoreDNS и Konnectivity в L2.

Проследите переход от Applications к Argo CD в L1 и затем к результату в L2. Теперь появляются ресурсы Cilium, CoreDNS и Konnectivity. Отличайте место работы контроллеров доставки от кластера назначения. После подготовки базового набора L2 можно передавать пользователю.

### 32. Передаём готовый кластер

[Показать шаг](platform-webinar-classic.html#chapter-6-step-5)

После подготовки стандартных аддонов платформа передаёт пользователю готовый Kubernetes. Путь исходного ClusterClaim завершён.

**Результат:** Пользователь получил готовый L2.

Вернитесь к исходному заказу: по заданной конфигурации подготовлены L1 и L2. Сделайте короткую паузу на результате. Для вопросов можно открыть общую карту: L0 координирует создание, L1 размещает инфраструктуру и control plane L2, L2 предоставляет Kubernetes API пользователю.

## 7. Разворачиваем приложение пользователя — 01:10

Как пользователь получает своё приложение в готовом L2?

### 33. Заказываем приложение

[Показать шаг](platform-webinar-classic.html#chapter-7-step-1)

Пользователь создаёт заказ на приложение. Платформа формирует AddonClaim в L0 и запускает уже знакомую цепочку доставки.

**Результат:** Заказ пользователя представлен ресурсом AddonClaim в L0.

L2 уже подготовлен. Теперь пользователь заказывает своё приложение, и по заказу появляется AddonClaim в L0. Покажите знакомое начало цепочки доставки. Конкретный способ оформления заказа здесь не требуется: важны заявка и дальнейшая работа контроллеров.

### 34. Создаём Addon приложения

[Показать шаг](platform-webinar-classic.html#chapter-7-step-2)

Контроллер AddonClaim обрабатывает заказ и создаёт Addon в L1. Этот ресурс описывает пользовательское приложение для L2.

**Результат:** В L1 создан Addon пользовательского приложения.

Сохраните заказ и AddonClaim в кадре. Результат обработки заявки — Addon в L1. Пока это ресурс с описанием приложения; следующим его подхватит AddonOperator. Различайте этот ресурс и фактически работающее приложение, которое появится в L2.

### 35. Создаём Applications приложения

[Показать шаг](platform-webinar-classic.html#chapter-7-step-3)

AddonOperator в L1 читает Addon и создаёт Applications. Argo CD получает описание того, что нужно развернуть в L2.

**Результат:** В L1 созданы Applications пользовательского приложения.

Покажите действие AddonOperator: из ресурса Addon появляются Applications в L1. Они передают Argo CD описание развёртывания. Цепочка доставки сохраняет ту же организацию, что и при подготовке базовых компонентов L2.

### 36. Запускаем приложение в L2

[Показать шаг](platform-webinar-classic.html#chapter-7-step-4)

Argo CD в L1 обрабатывает Applications и разворачивает ресурсы приложения в L2. Пользователь получает заказанное приложение.

**Результат:** Пользовательское приложение развёрнуто в L2.

Завершите цепочку результатом в L2: Argo CD развернул ресурсы пользовательского приложения. API L2 остаётся точкой доступа к управлению кластером, а новое приложение — отдельной рабочей нагрузкой. Вся история теперь ведёт от заказа кластера через его подготовку к заказу и запуску приложения пользователя.

## Завершение

Вернитесь к исходному заказу: ClusterClaim описывает целевое состояние, операторы доводят платформу до него, а статусы ресурсов позволяют подтвердить результат.

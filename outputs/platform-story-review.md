# Почему презентация стала последовательным рассказом

Новая [презентация платформы Beget](platform-story.html) построена как **7 глав и 36 событий примерно на 14 минут 30 секунд**. Она ведет слушателя от заказа кластера до приложения пользователя в L2: на каждом экране один участник выполняет действие, а затем появляется конкретный результат. Для выступления подготовлен [сценарий с заметками](platform-story-guide.md).

Независимый разбор предыдущей космической версии показал главную проблему: она хорошо приглашала исследовать архитектуру, но требовала слишком много самостоятельной работы от слушателя. Во время вебинара человек одновременно слушает речь и смотрит на экран. Если ему приходится искать очередной узел, разбираться в расположении уровней и читать мелкие подписи, причинная связь между действиями теряется.

У прежнего формата было несколько конкретных затруднений. Одинаковые планеты обозначали разные сущности — ресурсы, контроллеры и состояния. При перемещении камеры границы L0, L1 и L2 было трудно удерживать в памяти. Часть объектов показывалась заранее, поэтому результат очередного действия не всегда был заметен. Посещение этапа могло восприниматься как подтверждение его готовности. Вторичные подписи также уступали визуальным эффектам по заметности.

Поэтому новый вариант организован вокруг последовательности действий. Уровни постоянно занимают свои цветовые зоны: L0 управляет созданием, L1 размещает инфраструктуру и control plane L2, L2 предоставляет Kubernetes API пользователю. Объекты появляются постепенно. Уже знакомый результат становится исходной точкой следующего события: Cluster L1 приводит к запросу CAPI в облако, затем появляются машины, подтверждается инициализация и начинается bootstrap. Зритель может следить за этой цепочкой вместе с ведущим.

Изменилось и значение состояний. Переход к следующему событию показывает продвижение рассказа. Отметки готовности появляются только в предусмотренных сценарием точках. В частности, подтверждение инициализации control plane L2 в CAPI отделено от последующей установки Cilium, CoreDNS и Konnectivity и передачи готового кластера пользователю.

Параллельные процессы показаны явно. Фазы L1 идут параллельно настройке внешнего Vault: ClusterClaimOperator из L0 регистрирует каждый кластер в auth, создает точечные роли и привязки ServiceAccount L1, индивидуальные секреты и KMS transit для L2. Vault хранит настройки и предоставляет механизмы; запросы инициирует оператор. Рассказ переводит внимание между ними, сохраняя видимой вторую ветку: порядок объяснения не означает, что процессы выполняются строго один за другим. Отдельно видны CSR approver и CCM, которые создаются в L0 параллельно ресурсам Cluster L1 и Cluster L2.

Доставка Control plane L2 раскрыта по исполнителям: контроллер AddonClaim создает Addon (CP) в L1, AddonOperator создает Applications, а Argo CD разворачивает приложение. Финальная подготовка L2 также показана целиком: AddonClaim в L0 приводит к созданию Addon и Applications в L1, после чего Argo CD разворачивает Cilium, CoreDNS и Konnectivity в L2. После выдачи L2 та же цепочка раскрыта для заказа пользователя: AddonClaim → Addon → Applications → приложение в L2. API L2 при этом обозначает точку доступа к управлению, а приложение пользователя — отдельную рабочую нагрузку. Устройство control plane L2 получило собственную последовательность. Сначала показывается DaemonSet на нодах L1, затем общий etcd L1 и отдельный префикс для данных L2, после этого — API L2 и обратная передача статуса в CAPI. Такое разделение помогает объяснить место исполнения компонентов и роль обслуживаемого ими кластера.

Космическое оформление сохранено в переходах между главами. Короткий звездный перелет выполняется один раз; импульсы на новых связях завершаются максимум за 900 миллисекунд. После этого изображение остается спокойным, чтобы ведущий мог объяснить результат и сделать паузу. Навигация ручная: события и главы переключаются стрелками и кнопками внизу экрана. Заметки ведущего вынесены в отдельный сценарий.

Финальный независимый разбор оценил новую версию как подходящую для вебинара. По его дополнительным замечаниям исправлены два места: слова «сверху / снизу» в заметках согласованы с расположением параллельных веток, вторичные подписи увеличены и сделаны контрастнее. Основная последовательность признана понятной.

Предыдущие варианты сохранены отдельными копиями: [космическая версия со свободной картой](platform-flight-v1.html) и [исходная презентация](platform-webinar-classic.html). Новая версия предназначена для управляемого рассказа, а свободную карту можно использовать для самостоятельного знакомства с архитектурой.

Это **учебная схема по описанному командой процессу**, а не живой мониторинг инфраструктуры. Разбор оценивает структуру и читаемость презентации.
